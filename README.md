# ABCP Client

[![Сборка и тесты](https://github.com/miroslavkurb/da174-abcp-client/actions/workflows/build.yml/badge.svg)](https://github.com/miroslavkurb/da174-abcp-client/actions/workflows/build.yml)

Настольное приложение для Windows: забирает заказы из API ABCP, хранит их локально,
следит за появлением новых заказов и сменой статусов позиций, уведомляет пользователя
и готово к двустороннему обмену с 1С:УТ 11.4.

## Возможности

- список заказов с поиском (номер, номер в учётной системе, клиент, бренд, артикул),
  фильтрами по статусу и периоду;
- фоновая синхронизация по настраиваемому интервалу, догоняющая пропущенное;
- уведомления Windows о новых заказах и сменах статусов;
- журнал синхронизаций: что запрашивали, сколько получили, чем закончилось;
- карточка заказа по двойному щелчку: позиции с описаниями, свойствами и фото;
- импорт каталога магазина (YML) — заполняет карточки товаров **без обращений к API**;
- локальная база SQLite — приложение работает и показывает данные без сети;
- окно настроек: адрес API, реквизиты, таймаут, интервал опроса, уведомления, каталог.

## Требования

- Windows 10 версии 1809 (10.0.17763) или новее;
- .NET 8 Desktop Runtime для запуска, .NET 8 SDK для сборки;
- доступ к API ABCP: адрес хоста выдаёт менеджер ABCP, реквизиты —
  пользователь со статусом **API-администратор** (панель управления →
  Настройки → Система → «Данные для доступа к API»).

## Сборка и запуск

```powershell
dotnet build ABCPClient.sln
dotnet test  tests\ABCPClient.Tests\ABCPClient.Tests.csproj
dotnet run --project src\ABCPClient.UI
```

Публикация одним каталогом (нужен установленный .NET 8 Desktop Runtime):

```powershell
dotnet publish src\ABCPClient.UI -c Release -o publish
```

Один самодостаточный exe — рантайм внутри, ставить ничего не нужно:

```powershell
dotnet publish src\ABCPClient.UI -c Release -r win-x64 --self-contained `
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:EnableCompressionInSingleFile=true -p:DebugType=none -p:DebugSymbols=false `
  -p:GenerateDocumentationFile=false -o publish-single
```

Получается `ABCPClient.UI.exe` ≈ 85 МБ. Файл `appsettings.json` рядом не обязателен:
он задаёт лишь значения по умолчанию, а действующие настройки хранятся в локальной базе.

## Непрерывная сборка

`.github/workflows/build.yml` собирает решение и прогоняет тесты при каждом push
и pull request в `main`, плюс по кнопке (`workflow_dispatch`). Раннер — `windows-latest`:
интерфейс на WPF, а часть проектов нацелена на `net8.0-windows` (DPAPI, уведомления
Windows), поэтому на Linux решение не собирается в принципе. Результаты тестов
выкладываются артефактом `test-results` в формате `.trx`.

Стилевые правила из `.editorconfig` включены в сборку (`EnforceCodeStyleInBuild`),
поэтому расхождения со стилем видны в логе CI как предупреждения. Исключение —
каталог `Database/Migrations`: эти файлы генерирует `dotnet ef`, и править их
под общий стиль бессмысленно.

## Выпуск релиза

`.github/workflows/release.yml` собирает готовые файлы и выкладывает их в
[Releases](https://github.com/miroslavkurb/da174-abcp-client/releases). Два способа:

```powershell

git tag v1.0.1

```

либо вручную: **Actions → Релиз → Run workflow**, указать версию (`1.0.1`) и,
при необходимости, отметить предварительный выпуск. Тег в этом случае создаётся сам.

Версия обязана быть семантической (`1.2.3` или `1.2.3-beta.1`) — рабочий процесс
проверяет это до сборки и падает сразу, а не после двадцати минут работы.
Из тега версия подставляется в сборку (`-p:Version=…`) и попадает в свойства
исполняемого файла; значение по умолчанию в `Directory.Build.props` нужно только
для локальных сборок.

**Тесты выполняются до публикации**: артефакт с красными тестами хуже отсутствия
артефакта, поэтому падение тестов отменяет весь выпуск.

Что попадает в релиз:

| Файл | Что это |
|---|---|
| `ABCPClient-<версия>-win-x64.exe` | один самодостаточный файл, ≈85 МБ, рантайм внутри — ставить ничего не нужно |
| `ABCPClient-<версия>-win-x64-runtime-required.zip` | каталог сборки, ≈2 МБ, требует установленного .NET 8 Desktop Runtime |

Заметки к релизу формируются автоматически по коммитам с прошлого тега, поэтому
история выкачивается целиком (`fetch-depth: 0`). Релиз создаётся встроенным
токеном `GITHUB_TOKEN` — личные токены и сторонние действия не нужны.

Проверить контрольную сумму скачанного файла:

```powershell

```

## Первый запуск

1. Открыть **Настройки**.
2. Указать адрес API (например `https://demo.public.api.abcp.ru`), логин и пароль
   API-администратора. Вместо пароля можно вставить готовый md5-хэш.
3. Нажать **Проверить подключение** — приложение сохранит настройки, обратится к
   `cp/statuses` и загрузит справочник статусов.
4. Там же указать **адрес витрины** (например `https://da174.ru`) и **выгрузку
   каталога** магазина (YML), затем нажать **Импортировать каталог**. Это два
   бесплатных источника карточек: выгрузка закрывает собственное наличие, витрина —
   детали под заказ. Без них изображения тянутся из API по одному и упираются
   в ошибку 303.
5. Закрыть окно настроек. Фоновая синхронизация начнётся сама; кнопка
   **Синхронизировать** запускает её вручную.

Первая синхронизация забирает заказы за `Sync:InitialSyncDays` дней (по умолчанию 30 —
столько же API отдаёт без фильтра по дате).

## Где лежат данные

| Что | Путь |
|---|---|
| База SQLite | `%LOCALAPPDATA%\ABCPClient\abcpclient.db` |
| Журналы Serilog | `%LOCALAPPDATA%\ABCPClient\logs\abcpclient-<дата>.log` |
| Значения по умолчанию | `appsettings.json` рядом с исполняемым файлом |

Каталог данных вынесен из папки программы: при установке в `Program Files` она
недоступна на запись. Журналы хранятся 14 файлов с ротацией по дням.

## Настройки

`appsettings.json` задаёт значения по умолчанию, окно настроек пишет в таблицу
`Settings` локальной базы, и **значения из базы перекрывают файл**.

```jsonc
{
  "Abcp": {
    "BaseUrl": "",            // адрес API, выдаётся менеджером ABCP
    "Login": "",              // логин API-администратора
    "PasswordMd5": "",        // md5-хэш пароля (параметр userpsw)
    "TimeoutSeconds": 30,
    "RetryCount": 3,
    "PageSize": 500           // жёсткий предел ответа API — 1000 записей
  },
  "Sync": {
    "Enabled": true,
    "PollingIntervalSeconds": 120,
    "OverlapMinutes": 5,      // перекрытие окна выборки
    "InitialSyncDays": 30,
    "NotificationsEnabled": true,
    "ArticleCardRequestsPerMinute": 20,   // собственные лимиты на карточки товаров,
    "ArticleCardRequestsPerHour": 300,    // чтобы не упереться в ошибку 303
    "ArticleCardRequestsPerDay": 1500,
    "ArticleCardCooldownMinutes": 15      // пауза после ошибки 303
  },
  "Catalog": {
    "FeedPath": "",           // файл выгрузки каталога или её адрес
    "AutoImportHours": 0,
    "PrefetchImages": false,  // скачивать все изображения сразу при импорте
    "StorefrontUrl": "",      // адрес витрины: карточки деталей под заказ
    "StorefrontRequestsPerMinute": 60
  },
  "Database": { "FileName": "abcpclient.db" }
}
```

Переменные среды с префиксом `ABCPCLIENT_` тоже читаются, например
`ABCPCLIENT_Sync__PollingIntervalSeconds=300`.

## Безопасность реквизитов

API ABCP не использует токены и сессии: логин и md5-хэш пароля передаются параметрами
каждого запроса. Хэш поэтому равносилен паролю, и приложение обращается с ним как с секретом:

- в базе хранится только зашифрованным через **Windows DPAPI** (`CurrentUser` +
  привязка к приложению) — открытым текстом хэш на диск не попадает;
- в журналы уходит URL с `userpsw=***`, сам хэш не логируется никогда;
- при переносе базы на другую машину или в другой профиль Windows расшифровать
  секрет невозможно — приложение попросит ввести пароль заново. Это компромисс
  в пользу безопасности, а не сбой.

## Архитектура

```
ABCPClient.sln
├─ src/ABCPClient.Domain          сущности, перечисления, доменные правила (net8.0)
├─ src/ABCPClient.Application     контракты, DTO API, сценарии, разбор JSON (net8.0)
├─ src/ABCPClient.Infrastructure  клиент API, EF Core/SQLite, репозитории,
│                                 DPAPI, фоновая служба, слой интеграции (net8.0-windows)
├─ src/ABCPClient.UI              WPF, MVVM, уведомления (net8.0-windows10.0.19041.0)
└─ tests/ABCPClient.Tests         xUnit
```

Зависимости направлены внутрь: `UI → Infrastructure → Application → Domain`.
Домен не зависит ни от кого, `Application` не знает ни про HTTP, ни про базу.
Приложение живёт внутри `IHost`: он владеет контейнером DI, конфигурацией,
Serilog и фоновой службой. Окна и модели представления создаёт только контейнер.

### Как работает синхронизация

1. Окно выборки строится по `dateUpdatedStart` — этот фильтр API возвращает и новые,
   и изменённые заказы.
2. Нижняя граница = последняя сохранённая точка минус `OverlapMinutes`. Точка хранится
   **во времени портала** (как её отдаёт API), а не по часам локальной машины:
   иначе расхождение часовых поясов приводило бы к пропускам заказов.
3. Страницы читаются через `format=p`, который единственный отдаёт общее количество
   (`count`); без него API молча обрезает выдачу на 1000 записях. Заказы,
   попавшие в две страницы, отбрасываются по номеру.
4. Заказы применяются к базе: сопоставление по `number`, позиции — по `id` позиции.
   `itemKey` ключом не используется, он не уникален.
5. Смены `statusCode` позиций собираются в результат и пишутся в историю статусов —
   на них строятся уведомления.
6. Итог операции попадает в таблицу `SyncLog` и на вкладку «Журнал».

### Удалённые заказы

`cp/orders` по умолчанию **не возвращает удалённые заказы и позиции**, поэтому запросы
идут с `withDeleted=1`: иначе удаление заказа в панели управления выглядело бы как
«заказ просто перестал приходить», и он навсегда остался бы в локальной базе.

Отсутствие заказа в ответе удалением не считается: архивные заказы тоже не приходят
без `isArchive=1`. Такие заказы остаются в базе, а в журнал пишется предупреждение.

Заказ, удалённый раньше текущей точки продолжения, в окно по `dateUpdated` уже не попадёт,
поэтому есть отдельная сверка `ReconcileDeletedOrdersAsync`: она запрашивает сохранённые
номера пакетами по 100 с `withDeleted=1` и помечает удалённые. Запускается один раз за
сеанс работы фоновой службы и при каждом нажатии кнопки **Синхронизировать**. Сверка
всегда передаёт явный `dateCreatedStart`: без фильтра по дате API ограничивает выборку
последними 30 днями даже при точном совпадении номера.

### Статус заказа

В API ABCP **у заказа нет статуса** — статус есть только у позиции, и порядок статусов
в воронке API не сообщает (в `cp/statuses` есть флаги и цвет, но нет индекса сортировки).
Поэтому статус заказа вычисляется доменом честно и объяснимо: преобладающий статус —
самый частый среди позиций, при равенстве частот берётся меньший код; если статусов
несколько, заказ помечается смешанным и в таблице показывается «Статус (смешанный)».
Правило живёт в `OrderStatusAggregate`, а не в моделях представления.

### Обработка ошибок API

Ответ с кодом 400 и выше разбирается в `AbcpApiException` с полем `errorCode`.
Повторяются только временные сбои: транспорт, 5xx, 429 и `302` (кэш). Ошибки
`102`/`103`/`104` (реквизиты, права) и `1`–`4` (запрос) не повторяются: повтор их
не исправит, зато сожжёт лимиты вызовов API. Код `303` (лимит исчерпан) тоже не
повторяется — повтор только продлевает блокировку, паузу делает вызывающий код.

### Карточки товаров и лимит запросов API

В ответе `cp/orders` нет ни описаний, ни изображений — их отдаёт карточка товара,
а пакетная операция `cp/articles/info/batch` доступна не на каждом сайте (на нашем
она отвечает «Unknown operation»), поэтому карточки запрашиваются по одной через
`articles/info?format=bnpi`. Это быстро упирается в лимит вызовов и ошибку `303`.

Источники перебираются по возрастанию цены: **кэш → выгрузка каталога → витрина → API**.

1. **Кэш карточек** в таблице `ArticleCards`: артикул запрашивается один раз,
   отсутствие карточки тоже запоминается (`NotFound`), повторные открытия заказа
   лимит не тратят.
2. **Импорт каталога магазина.** Выгрузка YML из панели управления («Экспорт
   прайс-листа») содержит по каждому предложению бренд `vendor`, артикул
   `vendorCode`, описание, свойства `param`, изображения `picture` и штрихкоды
   `barcode` — тот же набор, что в карточке товара, но сразу по всему ассортименту
   и **без единого обращения к API**. На реальной выгрузке da174.ru: 8686 предложений
   → 8686 карточек, из них 5868 с изображением и 5038 со штрихкодом, около 2 секунд.
   Ограничение: в выгрузке только **собственное наличие**. Из 343 артикулов,
   встречающихся в заказах, в ней нашлись 53 — заказы почти целиком состоят
   из деталей под заказ.
3. **Витрина магазина** — то, что закрывает оставшиеся 290. Страница товара
   `{витрина}/parts/{бренд}/{артикул}` есть у всего, чем магазин торгует; изображение
   и наименование берутся из разметки Open Graph (`og:image`, `og:title`). Витрина —
   обычный сайт, а не API, поэтому лимит вызовов API её страницы **не расходуют**.
   У несуществующего товара страница отдаётся с кодом 200, но `og:*` пустые — это
   и есть признак «витрина такого не знает», и тогда очередь доходит до API.
   Адрес задаётся в настройках (`Catalog:StorefrontUrl`), частота ограничена
   60 страницами в минуту: это рабочий сайт магазина.
4. **Собственные лимиты API** на минуту, час и сутки. Счётчики хранятся **в базе**
   (`Sync:ArticleCardUsage`), а не в памяти: перезапуск приложения счётчики на
   стороне API не обнуляет, иначе после рестарта первое же открытие заказа снова
   упиралось бы в `303`. Там же хранится момент окончания паузы после `303`
   (`Sync:ArticleCardBlockedUntil`).

### Сопоставление артикулов между источниками

Один и тот же артикул записан по-разному: в заказе `ADW-0855`, в каталоге `ADW0855`;
`Sachs 3182 654 213` против `3182654213`. Поэтому у карточки кроме пары «бренд + номер»
есть **сопоставительный ключ** `ArticleCard.MatchKey` — бренд и номер без всех знаков,
кроме букв и цифр, в нижнем регистре (`ArticleKey.Match`). Поиск в кэше идёт по нему,
точное совпадение приоритетнее. Без этого карточка из каталога не находилась бы и
приложение зря шло в API; на живых данных так терялось 10 артикулов из 53 найденных.
Регистр в SQLite тоже значим при сравнении строк, и приведённый к нижнему регистру
ключ снимает заодно и эту проблему. Старым карточкам ключ проставляется разовым
проходом при запуске (`ArticleCardRepository.BackfillMatchKeysAsync`): вычислить его
в миграции нечем — убрать все знаки, кроме букв и цифр, средствами SQLite нельзя.

Сами изображения лежат на CDN и к API отношения не имеют: их загрузка лимит не
расходует. `ProductImageCache` понимает оба вида ссылок — имя файла от API
(`https://imgcdn.abcp.ru/p/{name}`) и полный адрес из выгрузки каталога; файл в кэше
для полного адреса именуется по хэшу адреса, чтобы одинаковые имена с разных хостов
не затирали друг друга.

### Готовность к 1С

Слой интеграции отделён: `IExchangeProvider` и заглушка `OneCExchangeProvider`
в `Infrastructure/Integration`. Код ABCP ничего не знает об 1С, обмен работает с
доменными сущностями. Связка заказов — пара «`number` ↔ `internalNumber`», которую
API отдаёт сам, поэтому собственный идентификатор обмена не нужен; фильтр
`internalNumbers[]` позволяет искать заказы по номерам учётной системы.

## Работа с базой

```powershell
# Новая миграция после изменения сущностей
dotnet dotnet-ef migrations add ИмяМиграции --project src\ABCPClient.Infrastructure --output-dir Database\Migrations

# Состояние миграций
dotnet dotnet-ef migrations list --project src\ABCPClient.Infrastructure
```

`dotnet-ef` установлен локальным инструментом (`.config/dotnet-tools.json`), версия
зафиксирована в репозитории. Миграции применяются автоматически при запуске
приложения; там же включается журнал **WAL** — без него чтение из интерфейса
блокировалось бы записью фоновой службы.

## Ограничения

- Каталоги и склады API (`/cp/ts/...`) не используются: приложение работает только
  с заказами, статусами и историей статусов.
- Форма узла `positions` в пакетной операции `cp/orders/statusHistory` в документации
  не описана; клиент разбирает оба возможных варианта и не падает при несовпадении,
  но окончательно это проверяется на живом ответе.
- Уведомления Windows требуют, чтобы они были разрешены в параметрах системы;
  сбой подсистемы уведомлений логируется и не прерывает синхронизацию.
