# Справочник по API ABCP

Документация: https://www.abcp.ru/wiki/ABCP.API (общая часть — `API:Docs`, нужные нам методы — `API.ABCP.Admin`).

## Транспорт и авторизация

- REST поверх HTTPS, обмен в UTF-8, ответ **только JSON**. В запросах передавать `Accept: application/json`.
- Чтение — GET, запись — POST с `Content-Type: application/x-www-form-urlencoded`.
- **Хост индивидуален для каждого сайта и выдаётся менеджером ABCP.** В документации примеры на `https://demo.public.api.abcp.ru`. Хост — обязательная настройка приложения (`ApiUrl`), хардкодить нельзя.
- Авторизация — параметрами каждого запроса: `userlogin` (логин) и `userpsw` = **md5-хэш пароля**, а не сам пароль. Отдельных токенов/сессий нет, ключ передаётся в каждом вызове.
- Все методы с префиксом `/cp/` работают **только** от пользователя со статусом *API-администратор*. Его логин и пароль владелец берёт в ПУ: Настройки → Система → «Данные для доступа к API» (`https://cp.abcp.ru/?page=allsettings&systemsettings&apiInformation`). Статистика вызовов API: `https://cp.abcp.ru/?page=cabinet&detailingServices`.
- Массивы передаются в стиле PHP: `positionsId[0]=...&positionsId[1]=...`.
- Даты — строки формата `ГГГГ-ММ-ДД ЧЧ:ММ:СС` во времени портала. Часовой пояс сервера считать неизвестным: хранить в БД полученную строку/`DateTime` без конвертаций и не пересчитывать в UTC самостоятельно.

### Требования безопасности для приложения

- В `Settings` хранить именно md5-хэш, а не пароль. Хэш — это полноценный секрет доступа (эквивалент пароля), поэтому шифровать его через Windows DPAPI (`ProtectedData`, scope `CurrentUser`), а не класть в SQLite открытым текстом.
- В логи Serilog никогда не писать `userpsw` и полный URL запроса с query-строкой — маскировать через enricher/destructuring. Логировать операцию, код ответа, длительность.

## Ошибки

Успех — HTTP 200. Любой код ≥400 — ошибка с телом:

```json
{ "errorCode": 102, "errorMessage": "User Authentication Error" }
```

| Код | Значение |
|---|---|
| 1 | ошибка синтаксиса запроса |
| 2 | не найден обязательный параметр |
| 3 | неизвестная операция |
| 4 | ошибка в параметре запроса |
| 13 | неизвестная ошибка |
| 102 | ошибка аутентификации пользователя |
| 103 | доступ запрещён |
| 104 | ошибка аутентификации сайта |
| 201 | ошибка данных |
| 202 | нарушение уникальности данных |
| 301 | объект не найден |
| 302 | ошибка кэша |
| 303 | ресурс заблокирован |

Политика Retry: повторять только транспортные сбои и 5xx (экспоненциальная задержка). Коды 102/103/104 и 1/2/3/4 — ошибки конфигурации или кода, повторять бессмысленно, их надо показывать пользователю и гасить опрос.

## Методы, на которых строится приложение

### `GET cp/orders` — список заказов

Фильтры: `dateCreatedStart`, `dateCreatedEnd`, `dateUpdatedStart`, `dateUpdatedEnd`, `numbers[]`, `internalNumbers[]`, `statusCode` (один или массив; отбирает заказы, где **хотя бы одна** позиция в этом статусе), `officeId`, `distributorId`, `distributorOrderId`, `userId`, `isCanceled`, `withDeleted`, `isArchive`, `limit`, `skip`, `desc`, `format`.

Значения `format`:

| Значение | Что делает |
|---|---|
| (нет) | заказы со полным составом позиций |
| `short` | без содержимого позиций |
| `count` | только количество заказов |
| `status_only` | номер заказа + по позициям: `id`, `statusCode`, `brand`, `number`, `numberFix`, `code`, `quantityFinal` |
| `additional` | + данные клиента при гостевом заказе, `vinQueryIds` у позиций |
| `p` | ответ-объект `{ items: [...], count: N }` — единственный способ узнать общее количество для пагинации |

**Важные ограничения:**

- по умолчанию отдаётся не более **1000** записей — обязательна пагинация через `format=p` + `limit`/`skip`;
- если фильтр по дате не задан вообще, сервер сам подставляет `dateCreatedStart` = последние 30 дней;
- по умолчанию возвращаются только неархивные заказы.

Ключевые поля заказа: `number` (онлайн-номер в портале), `internalNumber` (номер в учётной системе, т.е. в 1С), `clientOrderNumber`, `userId`, `userName`, `userFullName`, `userEmail`, `userMobile`, `userCode`, `positionsQuantity`, `sum`, `date`, `dateUpdated`, `comment`, `debt`, `paid`, `profileId`, `managerId`, `deliveryAddressId`/`deliveryAddress`, `deliveryOfficeId`/`deliveryOffice`, `deliveryTypeId`/`deliveryType`, `paymentTypeId`/`paymentType`, `deliveryCost`, `shipmentDate`, `basketId`/`basketName`, `wholeOrderOnly`, `code`, `isDelete`, `isOfficialDistributor`, `positions[]`, `notes[]`.

Поля позиции (`positions[]`): `id` (уникальный id позиции в портале), `code`, `brand`, `brandFix`, `number`, `numberFix`, `description`, `quantity`, `quantityFinal`, `priceIn`, `priceOut`, `oldPriceOut`, `priceRate`, `priceInSiteCurrency`, `currencyInId`, `currencyOutId`, `deadline`/`deadlineMax` (**часы**), `status`, `statusCode`, `statusChangeDate`, `dateUpdated`, `isCanceled`, `isDelete`, `comment`, `commentAnswer`, `routeId`, `dsRouteId`, `distributorId`, `distributorName`, `distributorType` (20 прайсовый, 22 онлайн, 21 дилерский прайс), `distributorOrderId`, `distributorOrderView`, `supplierCode`, `itemKey`, `lineReference`, `weight`.

`isCanceled` — запрос на удаление позиции: `0` не отправлялся, `1` отправлен клиентом, `2` отклонён менеджером.

### `GET cp/order` — один заказ

Параметры: `number` (обязателен) либо `internalNumber`, плюс `withDeleted`, `format` (`additional` — данные гостевого клиента, `locations` — полные коды мест хранения в `locationsFullCodes` у позиций с привязкой/бронью к партии).

### `GET cp/statuses` — справочник статусов

Без дополнительных параметров. Возвращает: `id` (**он же `statusCode`**), `name`, `comment` (описание для клиента), `notify`, `paid`, `startDelivery`, `delivery`, `placingOrder`, `color` (цвет статуса — использовать в UI-таблице).

Справочник кэшировать локально и обновлять по расписанию, а не на каждый опрос.

### `GET cp/order/statusHistory` и `GET cp/orders/statusHistory` — история статусов

- одиночная: `positionId`;
- пакетная: `positionsId[]` (позиции могут быть из разных заказов), ответ — узел `positions`.

Поля: `id` (в пакетном варианте), `statusCode`, `status`, `datetime`, `managerId`, `managerName`.

## Как это ложится на архитектуру приложения

- **Статус — атрибут позиции, а не заказа.** У объекта заказа поля `status`/`statusCode` нет вообще. Поэтому в `Orders.Status` держать *производное* значение (агрегат по позициям: например, «минимальный по воронке» статус или сводку «N позиций в статусе X»), и хранить рядом сырые статусы позиций в `OrderItems.Status`/`StatusCode`. Правило агрегации задокументировать в домене, а не размазывать по ViewModel.
- **`OrderPollingService` строить на `dateUpdatedStart`**: фильтр по дате обновления возвращает и новые, и изменённые заказы — ровно то, что нужно для инкрементальной синхронизации. Хранить в БД `LastSyncAt` (по времени портала, из полей ответа, а не по локальным часам) и запрашивать с небольшим перекрытием (например, минус 5 минут) — защита от заказов, обновлённых в ту же секунду, что и предыдущий срез.
- **Дешёвый опрос** — `format=status_only` (только статусы позиций) и `format=short` (без позиций); полный состав тянуть только для новых/изменённых заказов или по требованию UI. `format=count` — для показателя «Количество заказов» в статус-баре.
- **Пагинация обязательна**: цикл `format=p` → `count`, затем `limit`/`skip`. Считать 1000 жёстким верхним пределом одного ответа.
- **Идемпотентность и дедупликация**: `number` — стабильный ключ заказа, `positions[].id` — стабильный ключ позиции. `itemKey` **не уникален**, ключом не использовать.
- **Мост к 1С уже есть в API**: `internalNumber` (номер в учётной системе) и фильтр `internalNumbers[]`, плюс `clientOrderNumber`. Поэтому `IExchangeProvider` должен работать в терминах пары `number` ↔ `internalNumber`, а не придумывать свой идентификатор.
- **Уведомления** привязывать к переходу `statusCode` позиции и к появлению нового `number`; для истории перехода использовать пакетный `cp/orders/statusHistory`, чтобы не дёргать по позиции отдельным запросом.
- Полезно на будущее: `cp/orders/toArchive` / `cp/orders/fromArchive`, `cp/order/merge` (лимит 50 позиций за раз), `cp/orders/online` (отправка онлайн-заказа поставщику), `cp/users`, `cp/finance/*` (оплаты, баланс, лимит кредита), `cp/managers`, `cp/distributors`.
- **Карточки товаров дешевле брать не из API.** В `cp/orders` нет ни описаний, ни изображений — **ссылок на картинки в ответе заказа не существует**, у позиции только бренд, номер, описание, цены и статус. Пакетная `cp/articles/info/batch` на нашем сайте отвечает «Unknown operation» (код 3), поэтому остаётся `articles/info?format=bnpi` по одному артикулу — и лимит выбирается мгновенно: за всё время удалось получить 10 карточек, дальше всегда 303. Источники в порядке возрастания цены: кэш → выгрузка каталога → витрина → API.
- **Выгрузка каталога магазина** в YML («Экспорт прайс-листа» в ПУ) содержит `vendor` + `vendorCode` (это и есть ключ «бренд + артикул»), `description`, `param`, `picture` и `barcode` — весь набор карточки сразу по всему ассортименту и без запросов к API (`YmlCatalogImporter`). Но в ней только **собственное наличие**: из 343 артикулов в заказах нашлись 53. Штрихкодов в API нет вообще — выгрузка их единственный источник на стороне ABCP.
- **Витрина магазина закрывает остальное.** Страница `{витрина}/parts/{бренд}/{артикул}` есть у всего, чем магазин торгует, и отдаёт `og:image` и `og:title`. Это обычный сайт, лимит API не расходуется (`StorefrontArticleSource`). Несуществующий товар: HTTP 200 и пустые `og:*`. Проверено на живых артикулах — 8 из 8 с изображениями, ноль обращений к API.
- **Артикул пишется по-разному в разных источниках** (`ADW-0855` в заказе против `ADW0855` в каталоге, `3182 654 213` против `3182654213`). Поиск в кэше идёт по `ArticleCard.MatchKey` = `ArticleKey.Match` (только буквы и цифры, нижний регистр), точное совпадение приоритетнее. Сравнение строк в SQLite чувствительно к регистру, поэтому ключ приводится к нижнему регистру при сохранении, а не в запросе.
- **Счётчики лимита хранить в базе, а не в памяти.** Лимиты считает сервер API, перезапуск приложения их не обнуляет: собственные счётчики на минуту/час/сутки и момент окончания паузы после 303 лежат в таблице настроек (`Sync:ArticleCardUsage`, `Sync:ArticleCardBlockedUntil`).
- **Изображения к лимиту API отношения не имеют**: они на CDN и качаются отдельным `HttpClient` без реквизитов. Ссылки бывают двух видов — имя файла от API (`imgcdn.abcp.ru/p/{name}`) и полный адрес из выгрузки каталога (`pubimg.nodacdn.net`).
- Есть отдельный интерфейс **API TS** (`/cp/ts/...`) — склад/торговая система: приёмка, отгрузка, возвраты, платежи, доставки, маркировка. В текущую задачу не входит, но при расширении смотреть `API.TS.Admin`.

# Подготовка к интеграции с 1С

Очень важно.

Архитектура должна изначально предусматривать двусторонний обмен с 1С:УТ 11.4.

Не связывать код ABCP с кодом 1С.

Создать отдельный слой интеграции.

Интерфейс:

IExchangeProvider

Реализация-заглушка:

OneCExchangeProvider

В дальнейшем через него будет реализовано:

Из 1С:

- создание заказа;
- изменение заказа;
- изменение статусов;
- обновление цен;
- обновление остатков.

Из ABCP:

- новые заказы;
- изменение статусов;
- оплаты;
- комментарии;
- трек-номера.

Архитектура должна позволять без переписывания приложения добавить полноценный обмен.
