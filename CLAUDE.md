# Справочник по API ABCP

Документация: https://www.abcp.ru/wiki/ABCP.API (общая часть — `API:Docs`, нужные методы — `API.ABCP.Admin`).

## Транспорт и авторизация

- REST поверх HTTPS, UTF-8, ответ **только JSON**. Передавать `Accept: application/json`.
- Чтение — GET, запись — POST с `Content-Type: application/x-www-form-urlencoded`.
- **Хост свой у каждого сайта, выдаёт менеджер ABCP.** В доках примеры на `https://demo.public.api.abcp.ru`. Хост — обязательная настройка (`ApiUrl`), хардкод запрещён.
- Авторизация параметрами каждого запроса: `userlogin` и `userpsw` = **md5-хэш пароля**, не пароль. Токенов/сессий нет, ключ в каждом вызове.
- Методы с префиксом `/cp/` работают **только** от пользователя со статусом *API-администратор*. Логин и пароль владелец берёт в ПУ: Настройки → Система → «Данные для доступа к API» (`https://cp.abcp.ru/?page=allsettings&systemsettings&apiInformation`). Статистика вызовов: `https://cp.abcp.ru/?page=cabinet&detailingServices`.
- Массивы в стиле PHP: `positionsId[0]=...&positionsId[1]=...`.
- Даты — строки `ГГГГ-ММ-ДД ЧЧ:ММ:СС` во времени портала. Часовой пояс сервера неизвестен: хранить строку/`DateTime` как пришло, в UTC не пересчитывать.

### Требования безопасности для приложения

- В `Settings` хранить md5-хэш, не пароль. Хэш = полноценный секрет (эквивалент пароля), поэтому шифровать через Windows DPAPI (`ProtectedData`, scope `CurrentUser`), не класть в SQLite открытым текстом.
- В логи Serilog никогда не писать `userpsw` и полный URL с query — маскировать через enricher/destructuring. Логировать операцию, код ответа, длительность.

## Ошибки

Успех — HTTP 200. Код ≥400 — ошибка с телом:

```json
{ "errorCode": 102, "errorMessage": "User Authentication Error" }
```

| Код | Значение |
|---|---|
| 1 | ошибка синтаксиса запроса |
| 2 | не найден обязательный параметр |
| 3 | неизвестная операция |
| 4 | ошибка в параметре запроса |
| 13 | неизвестная ошибка |
| 102 | ошибка аутентификации пользователя |
| 103 | доступ запрещён |
| 104 | ошибка аутентификации сайта |
| 201 | ошибка данных |
| 202 | нарушение уникальности данных |
| 301 | объект не найден |
| 302 | ошибка кэша |
| 303 | ресурс заблокирован |

Retry: повторять только транспортные сбои и 5xx (экспоненциальная задержка). Коды 102/103/104 и 1/2/3/4 — ошибки конфигурации или кода, повтор бессмыслен: показать пользователю, опрос погасить.

## Методы, на которых строится приложение

### `GET cp/orders` — список заказов

Фильтры: `dateCreatedStart`, `dateCreatedEnd`, `dateUpdatedStart`, `dateUpdatedEnd`, `numbers[]`, `internalNumbers[]`, `statusCode` (один или массив; отбирает заказы, где **хотя бы одна** позиция в этом статусе), `officeId`, `distributorId`, `distributorOrderId`, `userId`, `isCanceled`, `withDeleted`, `isArchive`, `limit`, `skip`, `desc`, `format`.

Значения `format`:

| Значение | Что делает |
|---|---|
| (нет) | заказы со полным составом позиций |
| `short` | без содержимого позиций |
| `count` | только количество заказов |
| `status_only` | номер заказа + по позициям: `id`, `statusCode`, `brand`, `number`, `numberFix`, `code`, `quantityFinal` |
| `additional` | + данные клиента при гостевом заказе, `vinQueryIds` у позиций |
| `p` | ответ-объект `{ items: [...], count: N }` — единственный способ узнать общее количество для пагинации |

**Важные ограничения:**

- по умолчанию не более **1000** записей — пагинация через `format=p` + `limit`/`skip` обязательна;
- фильтр по дате не задан → сервер сам ставит `dateCreatedStart` = последние 30 дней;
- по умолчанию возвращаются только неархивные заказы.

Ключевые поля заказа: `number` (онлайн-номер в портале), `internalNumber` (номер в учётной системе, т.е. в 1С), `clientOrderNumber`, `userId`, `userName`, `userFullName`, `userEmail`, `userMobile`, `userCode`, `positionsQuantity`, `sum`, `date`, `dateUpdated`, `comment`, `debt`, `paid`, `profileId`, `managerId`, `deliveryAddressId`/`deliveryAddress`, `deliveryOfficeId`/`deliveryOffice`, `deliveryTypeId`/`deliveryType`, `paymentTypeId`/`paymentType`, `deliveryCost`, `shipmentDate`, `basketId`/`basketName`, `wholeOrderOnly`, `code`, `isDelete`, `isOfficialDistributor`, `positions[]`, `notes[]`.

Поля позиции (`positions[]`): `id` (уникальный id позиции в портале), `code`, `brand`, `brandFix`, `number`, `numberFix`, `description`, `quantity`, `quantityFinal`, `priceIn`, `priceOut`, `oldPriceOut`, `priceRate`, `priceInSiteCurrency`, `currencyInId`, `currencyOutId`, `deadline`/`deadlineMax` (**часы**), `status`, `statusCode`, `statusChangeDate`, `dateUpdated`, `isCanceled`, `isDelete`, `comment`, `commentAnswer`, `routeId`, `dsRouteId`, `distributorId`, `distributorName`, `distributorType` (20 прайсовый, 22 онлайн, 21 дилерский прайс), `distributorOrderId`, `distributorOrderView`, `supplierCode`, `itemKey`, `lineReference`, `weight`.

`isCanceled` — запрос на удаление позиции: `0` не отправлялся, `1` отправлен клиентом, `2` отклонён менеджером.

### `GET cp/order` — один заказ

Параметры: `number` (обязателен) либо `internalNumber`, плюс `withDeleted`, `format` (`additional` — данные гостевого клиента, `locations` — полные коды мест хранения в `locationsFullCodes` у позиций с привязкой/бронью к партии).

### `GET cp/statuses` — справочник статусов

Без параметров. Возвращает: `id` (**он же `statusCode`**), `name`, `comment` (описание для клиента), `notify`, `paid`, `startDelivery`, `delivery`, `placingOrder`, `color` (цвет статуса — использовать в UI-таблице).

Справочник кэшировать локально, обновлять по расписанию, не на каждый опрос.

### `GET cp/order/statusHistory` и `GET cp/orders/statusHistory` — история статусов

- одиночная: `positionId`;
- пакетная: `positionsId[]` (позиции могут быть из разных заказов), ответ — узел `positions`.

Поля: `id` (в пакетном варианте), `statusCode`, `status`, `datetime`, `managerId`, `managerName`.

## Как это ложится на архитектуру приложения

- **Статус — атрибут позиции, не заказа.** У заказа полей `status`/`statusCode` нет вообще. Поэтому в `Orders.Status` держать *производное* значение (агрегат по позициям: например «минимальный по воронке» статус или сводку «N позиций в статусе X»), рядом хранить сырые статусы позиций в `OrderItems.Status`/`StatusCode`. Правило агрегации задокументировать в домене, не размазывать по ViewModel.
- **`OrderPollingService` строить на `dateUpdatedStart`**: фильтр по дате обновления возвращает и новые, и изменённые заказы — ровно то, что нужно для инкрементальной синхронизации. Хранить в БД `LastSyncAt` (по времени портала, из полей ответа, не по локальным часам), запрашивать с перекрытием (например минус 5 минут) — защита от заказов, обновлённых в ту же секунду, что предыдущий срез.
- **Дешёвый опрос** — `format=status_only` (только статусы позиций) и `format=short` (без позиций); полный состав тянуть только для новых/изменённых заказов или по требованию UI. `format=count` — для «Количество заказов» в статус-баре.
- **Пагинация обязательна**: цикл `format=p` → `count`, затем `limit`/`skip`. 1000 — жёсткий верхний предел одного ответа.
- **Идемпотентность и дедупликация**: `number` — стабильный ключ заказа, `positions[].id` — стабильный ключ позиции. `itemKey` **не уникален**, ключом не использовать.
- **Мост к 1С уже есть в API**: `internalNumber` (номер в учётной системе) и фильтр `internalNumbers[]`, плюс `clientOrderNumber`. Поэтому `IExchangeProvider` работает в терминах пары `number` ↔ `internalNumber`, свой идентификатор не выдумывать.
- **Уведомления** привязывать к переходу `statusCode` позиции и к появлению нового `number`; для истории перехода брать пакетный `cp/orders/statusHistory`, не дёргать по позиции отдельно.
- Полезно на будущее: `cp/orders/toArchive` / `cp/orders/fromArchive`, `cp/order/merge` (лимит 50 позиций за раз), `cp/orders/online` (отправка онлайн-заказа поставщику), `cp/users`, `cp/finance/*` (оплаты, баланс, лимит кредита), `cp/managers`, `cp/distributors`.
- **Карточки товаров дешевле брать не из API.** В `cp/orders` нет ни описаний, ни изображений — **ссылок на картинки в ответе заказа не существует**, у позиции только бренд, номер, описание, цены, статус. Пакетная `cp/articles/info/batch` на нашем сайте отвечает «Unknown operation» (код 3), остаётся `articles/info?format=bnpi` по одному артикулу — лимит выбирается мгновенно: за всё время получено 10 карточек, дальше всегда 303. Источники по возрастанию цены: кэш → выгрузка каталога → витрина → API.
- **Выгрузка каталога магазина** в YML («Экспорт прайс-листа» в ПУ) содержит `vendor` + `vendorCode` (ключ «бренд + артикул»), `description`, `param`, `picture`, `barcode` — вся карточка сразу по всему ассортименту, без запросов к API (`YmlCatalogImporter`). Но там только **собственное наличие**: из 343 артикулов в заказах нашлись 53. Штрихкодов в API нет вообще — выгрузка их единственный источник на стороне ABCP.
- **Витрина магазина закрывает остальное.** Страница `{витрина}/parts/{бренд}/{артикул}` есть у всего, чем магазин торгует, отдаёт `og:image` и `og:title`. Обычный сайт, лимит API не расходует (`StorefrontArticleSource`). Несуществующий товар: HTTP 200 и пустые `og:*`. Проверено на живых артикулах — 8 из 8 с изображениями, ноль обращений к API.
- **Артикул пишется по-разному в разных источниках** (`ADW-0855` в заказе против `ADW0855` в каталоге, `3182 654 213` против `3182654213`). Поиск в кэше по `ArticleCard.MatchKey` = `ArticleKey.Match` (только буквы и цифры, нижний регистр), точное совпадение приоритетнее. Сравнение строк в SQLite чувствительно к регистру, поэтому ключ приводится к нижнему регистру при сохранении, не в запросе.
- **Счётчики лимита хранить в базе, не в памяти.** Лимиты считает сервер API, перезапуск приложения их не обнуляет: свои счётчики на минуту/час/сутки и момент конца паузы после 303 лежат в таблице настроек (`Sync:ArticleCardUsage`, `Sync:ArticleCardBlockedUntil`).
- **Изображения к лимиту API отношения не имеют**: они на CDN, качаются отдельным `HttpClient` без реквизитов. Ссылки двух видов — имя файла от API (`imgcdn.abcp.ru/p/{name}`) и полный адрес из выгрузки каталога (`pubimg.nodacdn.net`).
- Есть отдельный интерфейс **API TS** (`/cp/ts/...`) — склад/торговая система: приёмка, отгрузка, возвраты, платежи, доставки, маркировка. В текущую задачу не входит, при расширении смотреть `API.TS.Admin`.

## Решения, принятые по ходу

Каждое противоречит «очевидному» решению — без новых данных не пересматривать.

- **Карточки товаров не брать из API.** Лимит `articles/info` на этом сайте практически
  нулевой: 303 приходит с первого запроса за сутки. Пакетная `cp/articles/info/batch`
  отвечает «Unknown operation». Источники по возрастанию цены: локальный кэш, выгрузка
  каталога магазина (YML), **витрина da174.ru** (`og:image` со страницы товара, лимита
  нет), API последним. Штрихкодов в API нет вовсе — только в выгрузке каталога.
- **Счётчики лимита в базе, не в памяти.** Лимиты считает сервер API, перезапуск
  программы их не обнуляет.
- **Артикул пишется по-разному в разных источниках** (`ADW-0855` против `ADW0855`). Поиск в кэше
  по `ArticleCard.MatchKey` — только буквы и цифры в нижнем регистре.
- **Узел склада живёт внутри настольной программы**, не отдельной службой: у ПК и телефона
  разные базы, обмениваться нечем, а второй процесс делил бы тот же файл SQLite. Следствие
  показано на вкладке: закрыли программу — терминалы отключились.
- **Подключение терминала по одноразовому коду**, не по паролю. В базе только хэш
  токена; узел принимает обращения только из частных подсетей.
- **Узел работает по HTTP без шифрования** осознанно: его адрес — IP компьютера, который
  меняется, сертификат ставить негде. Поэтому приложению нужен `android:usesCleartextTraffic`,
  иначе браузер узел открывает, а приложение сообщает об отсутствии связи.
- **Наличие товара** определяется кодами статусов позиций из настроек `Picking:InStockStatusCodes`
  и `Picking:IncomingStatusCodes`. Неизвестный статус даёт «нет данных», не «нет в наличии».
- **Задание — одно на заказ**, повторное не создаётся. Закрывается, когда собрано всё доступное:
  строки в пути собрать нельзя. Отметка сборки идемпотентна — количество задаётся, не прибавляется.
- **Обрезка кода и AOT в Android отключены.** EF Core и внедрение зависимостей работают через
  отражение, обрезанная сборка падает уже на устройстве.
- **`global.json` закрепляет SDK 8.** На сервере сборки есть и SDK 10, а он считает
  `net8.0-android` снятым с поддержки и прерывает восстановление.

## Ловушки, на которые уже наступили

- `Application` как базовый тип в MAUI совпадает с пространством имён `ABCPClient.Application` —
  писать полным именем.
- Страницы, переданные в конструктор `App` параметрами, создаются раньше `InitializeComponent`,
  то есть раньше ресурсов приложения: любой `StaticResource` в разметке падает. Оболочка
  запрашивается из контейнера в теле конструктора.
- Kestrel слушает двойным стеком, поэтому адрес клиента IPv4 приходит как `::ffff:192.168.0.55`.
  Проверка частных подсетей обязана разворачивать его.
- Цвета в разметке заданы через `AppThemeBinding` прямо в атрибутах, не ресурсами: так не
  возвращается зависимость от порядка инициализации.

## Ждёт данных от заказчика

## Чего нельзя проверить здесь

Терминала сбора данных нет: экраны приложения на живом устройстве не проверялись. Узел
проверяется сквозным прогоном по HTTP. На реальном терминале нужно прогнать сканирование
аппаратным сканером, обрыв Wi-Fi во время отметки и два терминала на одном задании.
